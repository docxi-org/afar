# 01. Замысел

## Проблема

Far Manager — эффективный инструмент работы с файлами, но ИИ-агенты в него не встраиваются естественно:

- нет встроенного терминала: внешняя программа (например, `claude`) при запуске захватывает весь экран, а Far блокируется до её завершения;
- плагины не получают событий о файловых операциях, смене каталога с путём, выполненных командах — агенту нечего «видеть»;
- окна редактора и просмотрщика жёстко полноэкранные, «прикреплённой» области для агента нет;
- внешнего канала управления (IPC) нет.

Подробно — в [07-far-reference.md](07-far-reference.md). Обойти это можно только глубокой переделкой ядра Far (~200 тыс. строк C++). Вместо этого строим новое приложение, сохраняя то, за что ценят Far: две панели, раскладку клавиш, внешний вид и скорость работы с клавиатуры.

## Цель

Консольный файловый менеджер, в котором пользователь и ИИ-агент работают **в одном пространстве**:

- пользователь видит агента постоянно (нижняя панель) и переключается на него одной клавишей;
- агент знает, что делает пользователь (журнал событий), — сразу или по запросу;
- агент может действовать *через интерфейс менеджера* (перейти в каталог, выделить файлы, открыть файл на нужной строке, показать сравнение) — так пользователь видит, что происходит;
- агент может действовать и *своими средствами* (собственные инструменты Claude Code для чтения/правки файлов и запуска команд) — эти действия тоже попадают в журнал и отражаются в панелях.

## Цели (что должно получиться)

1. **Привычность для пользователя Far.** Синие панели, рамки, строка меню, командная строка, строка функциональных клавиш; основные сочетания клавиш как в Far.
2. **Агент — часть приложения.** Отдельная панель на всю ширину под файловыми панелями, видна всегда, в том числе при работе во встроенном просмотрщике.
3. **Единый слой команд.** Любое действие пользователя или агента — команда с именем и параметрами; все команды журналируются.
4. **Наблюдаемость.** Структурированный журнал событий: навигация, выделение, файловые операции и их результаты, команды и коды возврата, открытие/сохранение файлов, внешние изменения ФС.
5. **Управляемость.** MCP-сервер внутри приложения: агент читает состояние и вызывает команды.
6. **Асинхронность.** Ни одна операция не блокирует интерфейс: копирование идёт в фоне, команды выполняются во встроенном терминале, агент работает параллельно.
7. **Надёжность файловых операций.** Копирование/перемещение/удаление не теряют данные; ошибки обрабатываются явно; удаление по умолчанию — в корзину.

## Не-цели

- **Полная функциональная совместимость с Far.** Реализуем те ~20% функций, которыми пользуются ~80% времени; остальное — по мере надобности.
- **Совместимость с плагинами Far.** API плагинов Far не воспроизводится.
- **Совместимость с макросами Far (LuaMacro).** Возможно, позже — собственный механизм расширений.
- **Графический интерфейс.** Только консоль (TUI), работающая в Windows Terminal / conhost / любом современном эмуляторе терминала.
- **Собственная LLM-логика.** Агент — это Claude Code; afar не реализует цикл агента, а предоставляет ему среду, инструменты и контекст. (Структурированный режим чата поверх `claude -p --output-format stream-json` рассматривается как возможное развитие — см. [04-agent.md](04-agent.md#развитие-структурированный-режим).)

## Принципы

1. **Команда — единица действия.** Если что-то можно сделать клавишей, это можно сделать и командой агента, и наоборот (с учётом политики разрешений).
2. **Журнал — единый источник правды о том, что происходило.** Пишется всегда; флаг «агент видит в реальном времени» влияет только на то, *передаётся* ли журнал агенту автоматически.
3. **Агент показывает — пользователь подтверждает.** Разрушительные действия, инициированные агентом через afar, требуют подтверждения пользователя (настраивается).
4. **Интерфейс не блокируется никогда.** Долгие операции — в фоновых задачах с прогрессом.
5. **Far — эталон, а не догма.** Повторяем поведение Far там, где оно удобно и привычно; отступаем, где мешает архитектура или есть заметно лучшее решение.
6. **Кроссплатформенность по умолчанию, Windows — в первую очередь.** Платформенные различия изолированы в отдельных модулях.

## Сценарии

### С1. «Что я тут делал?»
Пользователь полчаса разбирал папку с проектом: перемещал файлы, удалял лишнее, запускал сборку. Переключается в панель агента и спрашивает: «Что я поменял в структуре проекта и не сломал ли сборку?» Агент читает журнал (перемещения, удаления, команду `cargo build` с кодом возврата 101), смотрит вывод сборки и объясняет, какой перенос сломал импорт.

### С2. «Покажи»
Пользователь: «Где обрабатываются ошибки авторизации?» Агент ищет по коду своими средствами, затем через afar переводит левую панель в нужный каталог, ставит курсор на файл и открывает его в просмотрщике на нужной строке.

### С3. «Разложи по папкам»
Пользователь выделяет 200 файлов и просит разложить их по годам. Агент формирует план, через afar создаёт папки и *выделяет* группы файлов; пользователь видит план в панелях и подтверждает перемещение одним диалогом (операция исполняется движком afar с прогрессом и обработкой конфликтов).

### С4. Живое сопровождение
Флаг «агент видит в реальном времени» включён. Пользователь удалил файл, запустил тесты — упали. Он пишет агенту: «почему?» — и агенту не нужно ничего объяснять: удаление и вывод тестов уже в контексте запроса.

### С5. Агент правит код
Агент своими инструментами правит три файла. afar получает события об этих правках (через хук Claude Code), подсвечивает изменённые файлы в панелях и записывает правки в журнал с пометкой «агент». Пользователь по F3 смотрит результат.

## Критерии успеха

- Пользователь Far садится за afar и выполняет навигацию, копирование, перемещение, удаление, просмотр файлов, запуск команд без чтения документации.
- Агент отвечает на вопросы о недавних действиях пользователя без пересказа с его стороны.
- Агент может «показать» файл/место в коде через интерфейс afar.
- Интерфейс не замирает ни во время копирования больших объёмов, ни во время работы агента, ни во время выполнения команд.
